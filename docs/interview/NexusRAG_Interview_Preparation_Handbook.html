Executive Overview & Problem Solved

NexusRAG is a production-aligned Retrieval-Augmented Generation system that eliminates LLM hallucinations and bridges institutional knowledge freshness.

1.1 What is NexusRAG?

NexusRAG (Genworx Knowledge Assistant) is an enterprise-grade AI assistant engineered to perform grounded question-answering over private institutional documents. Built on a modern decoupled stack—React 18 single-page frontend, FastAPI asynchronous backend, ChromaDB vector database, Redis distributed query cache, Google Gemini Embedding 2, and Google Gemini 2.5 Flash via the OpenRouter API gateway—NexusRAG enables knowledge workers to upload internal documents (PDFs, Markdown, text files) and query them through a natural-language chat interface with strict citation attribution.

1.2 Core Business Problems Solved

General-purpose foundation models (e.g., ChatGPT, Claude, Gemini) suffer from three fundamental architectural limitations when applied to enterprise workflows:

  • LLM Hallucinations: Foundation models generate plausible-sounding but factually fabricated statements when answering questions outside their training data or when probabilistic token sampling drifts.
  • Training Cutoff & Static Knowledge: Foundation models possess static weights frozen at training time. They are completely blind to company-specific policies, internal handbooks, project specifications, and recent updates.
  • Absence of Verifiable Citations: Off-the-shelf LLMs cannot provide verifiable document and page-level provenance. Users cannot confirm whether an answer is grounded in an official company document.

NexusRAG resolves these failure modes by decoupling reasoning from memory. The LLM acts strictly as a reasoning engine over external context retrieved deterministically from a local vector store.

US-01 Actor: Knowledge Base Administrator
Document Upload & Automated Indexing

Trigger: Admin selects and uploads a PDF, TXT, or MD document in DocumentsPage.

Preconditions: Document size <= 10MB; valid file extension; backend is healthy.

Technical Flow:
  1. DocumentsPage sends multipart/form-data POST to /api/v1/upload.
  2. Backend validates extension and size, then stages file to ./data/uploads/{uuid}_{filename}.
  3. DocumentService selects appropriate loader (PyPDFLoader for PDF, TextLoader for text/markdown).
  4. Extracted text is sanitized via helpers.clean_text (whitespace normalization, empty check).
  5. RecursiveCharacterTextSplitter splits text into 800-character chunks with 100-character overlap.
  6. GeminiEmbeddingService batches chunks (size 100) and calls gemini-embedding-2 for 768-dim vectors.
  7. ChromaStore upserts vectors and metadata into collection nexusrag_documents.
  8. Redis query cache is purged to prevent stale answers; staged upload file is unlinked in finally block.
Result:

Document appears in document table with verified physical chunk count and timestamp.

Failure Cases:

File > 10MB (413); invalid extension (400); zero extractable text (422); embedding 429 (502).

US-02 Actor: Knowledge Worker
Grounded Question Answering with Citations

Trigger: User types a natural-language question into ChatInput and presses Enter.

Preconditions: At least one document has been indexed into ChromaDB; Redis and LLM gateway reachable.

Technical Flow:
  1. ChatInput dispatches question through useChat hook to services/api.js.
  2. HTTP POST /api/v1/chat sends JSON payload { 'query': '...' } to FastAPI.
  3. routes_chat.py receives request, validates schema, and invokes RAGPipeline.query().
  4. RAGPipeline normalizes query and checks RedisQueryCache.get() (returns in <10ms on HIT).
  5. On MISS: Retriever calls GeminiEmbeddingService.embed_query() to produce a 768-dim vector.
  6. ChromaStore performs similarity search using Euclidean distance and returns Top-K=4 chunks.
  7. Empty context check: if 0 chunks retrieved, pipeline returns deterministic refusal without calling LLM.
  8. Grounded prompt template formats retrieved chunks with source and page markers.
  9. OpenRouterLLMService sends prompt to google/gemini-2.5-flash (temperature 0.2, max_tokens 4096).
  10. Citations are extracted and deduplicated at the (source, page) level.
  11. Response is serialized to JSON and stored in Redis with TTL=3600 seconds.
  12. HTTP 200 JSON RAGResponse returned to React UI; ConversationContext appends answer to chat history.
Result:

User receives a factually grounded answer with clickable source and page badges.

Failure Cases:

Empty query (422); Redis down (fail-open to RAG); LLM quota exceeded (502).

US-05 Actor: Knowledge Base Administrator
Safe Document Replacement (Atomic Re-indexing)

Trigger: Admin selects 'Replace Document' for an existing file with a newer version.

Preconditions: Target document currently exists in the knowledge base; new file passes validation.

Technical Flow:
  1. Frontend dispatches PUT /api/v1/documents/{filename} with new file payload.
  2. routes_documents.py verifies target document exists in ChromaDB (returns 404 if absent).
  3. New file is saved to an isolated staged path: ./data/uploads/{uuid}_{filename}.
  4. New file is ingested, parsed, chunked, embedded, and indexed into ChromaDB FIRST.
  5. If indexing fails: staged file is removed, old vectors are KEPT INTACT in ChromaDB, error returned.
  6. If indexing succeeds: backend queries and purges all old vectors matching the target filename.
  7. Entire Redis query cache is cleared to eliminate stale answers based on the old version.
  8. Staged file is deleted; HTTP 200 OK returned with updated chunk count and timestamp.
Result:

Knowledge base seamlessly transitions to new document version with zero data loss on failure.

Failure Cases:

Target missing (404); replacement embedding timeout (502; old document preserved).

3.3 5-Minute Technical Deep Dive Walkthrough

For senior system design rounds, structure your 5-minute explanation sequentially across these eight architectural layers:

  1. Client & Persistence Layer: React 18 SPA built with Vite, utilizing a centralized ConversationContext backed by browser localStorage under key nexusrag:chat-history:v1, allowing multi-turn conversations to survive page reloads.
  2. API & Concurrency Model: FastAPI running on Uvicorn ASGI. Endpoints use asynchronous defs for I/O operations and route blocking synchronous tasks (like ChromaDB disk writes) to AnyIO thread pools to keep the event loop responsive.
  3. Ingestion & Chunking Strategy: File staging to isolated paths prevents race conditions. Text is normalized and split with chunk_size=800 and chunk_overlap=100 to balance semantic coherence against prompt context window saturation.
  4. Vector Embeddings: Google Gemini Embedding 2 with 768 output dimensions and batch size 100. Overcomes OpenAI rate limits while providing superior retrieval accuracy for asymmetric query-document matching.
  5. Vector Storage & Physical Counting: ChromaDB PersistentClient. We enforce physical vector counting as the single source of truth for document chunk tallies, preventing UI metadata masking.
  6. Distributed Query Caching: Redis distributed cache with SHA-256 query keys and 3600-second TTL. Implements fail-open exception handling: socket timeouts log a warning and fall through to RAG without failing the query.
  7. LLM Reasoning Gateway: OpenRouter gateway routing to Google Gemini 2.5 Flash with sampling temperature 0.2. Automatic exponential backoff retries transient 429/5xx errors up to 3 times.
  8. Operational Rigor & Testing: 184 backend Pytest unit and integration tests + 52 frontend Vitest tests (236 total, 100% passing). Complete test doubles for Redis, ChromaDB, and model APIs guarantee zero external network dependencies during automated CI/CD runs.

4.1 Architectural Design Principles

  • Strict Layered Decoupling: API routes never touch ChromaDB or external APIs directly. All domain operations pass through RAGPipeline or DocumentService, which consume abstract interfaces for vector storage, caching, and model completion.
  • Fail-Open Resilience: Non-critical infrastructure failures (such as Redis downtime) gracefully degrade performance without stopping core question-answering functionality.
  • Deterministic Data Contracts: Strict Pydantic models validate incoming payloads and outgoing responses at the API boundary, rejecting malformed queries before downstream execution.
  • Test Double Isolation: The entire backend can be tested in offline mode using mock LLMs, in-memory fake Redis, and ephemeral ChromaDB collections.

Text Sanitization & Normalization

Pre-chunking text cleaning to eliminate non-printable artifacts, trailing spaces, and excessive whitespace.

Extracted raw text often contains layout artifacts, inconsistent newline sequences, and redundant whitespace that inflate token counts and distort embedding vectors. The helper function helpers.clean_text() applies deterministic sanitization rules: 

def clean_text(raw_text: str) -> str:
    if not raw_text:
        return ""
    # Strip leading/trailing whitespace
    text = raw_text.strip()
    # Normalize multiple newlines to double newlines (paragraph preservation)
    text = re.sub(r'\n{3,}', '\n\n', text)
    # Collapse consecutive horizontal whitespace (spaces/tabs) to a single space
    text = re.sub(r'[ \t]+', ' ', text)
    return text
ℹ️ WHY CLEAN TEXT BEFORE CHUNKING?

Whitespace characters consume embedding tokens without contributing semantic meaning. Collapsing multiple spaces and non-standard newlines ensures that the 800-character chunk window is densely packed with informative semantic tokens.

Recursive Character Chunking Strategy

Hierarchical text splitting maintaining natural paragraph, sentence, and word boundaries with context overlap.

12.1 Why Recursive Character Text Splitting?

Fixed-character chunking arbitrarily cuts sentences and words in half, destroying grammatical and semantic cohesion. NexusRAG employs LangChain's RecursiveCharacterTextSplitter with a hierarchical list of separators: 

separators = ["\n\n", "\n", " ", ""]

The splitter attempts to split at double newlines (paragraphs) first. If a paragraph exceeds 800 characters, it falls back to single newlines (lines), then spaces (words), and only splits mid-character as a last resort.

Embedding Service Deep Dive (Google Gemini Embedding 2)

768-dimensional dense vector embeddings with batching optimizations and asymmetric task-type projection.

14.1 Why Google Gemini Embedding 2?

NexusRAG selected Google's gemini-embedding-2 (via the official google-genai SDK) as its primary embedding engine based on three technical justifications:

  • Native Multilingual & Technical Density: Excels at enterprise documentation containing mixed prose, tabular data, code snippets, and acronyms.
  • 768 Output Dimension: Provides higher semantic expressiveness than standard 384-dim open-source models while requiring 50% less memory and disk footprint than 1536-dim OpenAI models.
  • Matryoshka Representation Learning: Supports flexible dimension truncation without catastrophic loss of retrieval accuracy.

14.2 Batching Optimization & Asymmetric Task Types

Embedding APIs incur significant HTTP round-trip latency if called per-chunk. GeminiEmbeddingService batches chunk embeddings in groups of 100 (batch_size = 100). A 35-page document producing 140 chunks is embedded in just 2 network calls rather than 140.

Crucially, the embedder distinguishes between document chunks and user queries using asymmetric task types:

  • Documents: Embedded with task type RETRIEVAL_DOCUMENT (optimizes declarative passages).
  • Queries: Embedded with task type RETRIEVAL_QUERY (optimizes interrogative prompts).

Asymmetric projection ensures questions and answers map into the same semantic neighborhood despite linguistic structural differences.

Vector Database Architecture (ChromaDB & ChromaStore)

Persistent embedded vector database utilizing SQLite metadata catalog and HNSW index with Euclidean distance.

15.1 ChromaStore Abstraction Layer

Directly coupling application routes to third-party vector store APIs creates fragile code that breaks on upstream version updates. NexusRAG implements ChromaStore (backend/app/vectordb/chroma_store.py) as an explicit domain abstraction over ChromaDB's PersistentClient.

Key responsibilities of ChromaStore include:

  • Persistent Directory Binding: Automatically mounts local disk directory ./data/chroma_db with SQLite storage.
  • Collection Isolation: Maintains all enterprise knowledge in a dedicated collection (nexusrag_documents).
  • Physical Record Source of Truth: Computes document chunk tallies by executing physical collection queries (collection.get(where={"source": filename})) rather than trusting cached metadata tags.
  • Deterministic Chunk ID Generation: Generates chunk IDs as {source}_chunk_{index} to ensure idempotency on repeated upserts.

15.2 Distance Metric: Euclidean Squared Distance (L2)

ChromaDB computes vector similarity using squared Euclidean distance ($L_2$ norm):

d(u, v) = ∑ (u_i - v_i)²

A distance of 0.0 indicates identical vectors, with smaller distances representing closer semantic proximity. Retrieved results are ranked in ascending order of distance, returning the closest Top-4 chunks to the RAG pipeline.

18.1 Why Top-K = 4?

The number of context chunks retrieved per query ($K$) directly dictates context completeness, prompt token overhead, and LLM attention distraction:

  • Context Sufficiency: At 800 characters per chunk, 4 chunks provide ~3,200 characters (~800 tokens) of rich contextual evidence. This easily spans multi-paragraph policies or multi-page technical workflows.
  • Preventing "Lost in the Middle": Research demonstrates that foundation models suffer from degraded recall when relevant facts are buried in large context windows ($K \ge 10$). Restricting $K=4$ forces the retriever to inject only top-tier relevant passages.
  • Cost & Latency Control: 4 chunks consume ~800 prompt tokens, keeping LLM generation latency under 1.5 seconds and minimizing per-query API expenditure.

Source Citation Attribution & Deduplication

Deterministic citation extraction eliminating redundant document tags while preserving page numbers.

If the retriever pulls Chunks 1, 2, and 3 from handbook.pdf (all from Page 4) and Chunk 4 from handbook.pdf (Page 5), naive citation builders would list handbook.pdf four times.

RAGPipeline executes deduplication over (source, page) tuples: 

def _deduplicate_sources(chunks: List[Document]) -> List[SourceCitation]:
    seen = set()
    citations = []
    for chunk in chunks:
        source = chunk.metadata.get("source", "unknown")
        page = chunk.metadata.get("page", 1)
        key = (source, page)
        if key not in seen:
            seen.add(key)
            citations.append(SourceCitation(source=source, page=page))
    return citations

The user interface receives a clean, deduplicated list:

  • handbook.pdf (Page 4)
  • handbook.pdf (Page 5)

This guarantees clean, professional citation UI badges while ensuring readers know exactly which pages support the generated response.

FastAPI Backend Architecture & Concurrency Model

Asynchronous event loop mechanics, non-blocking I/O execution, and thread pool worker delegation.

22.1 Asynchronous Event Loop vs Blocking Operations

FastAPI runs on Uvicorn ASGI using Python's standard asyncio event loop. Because Python's event loop is single-threaded, executing a CPU-intensive operation or a blocking synchronous network/disk call inside an async def route halts all concurrent request processing.

In NexusRAG, operations are categorized by concurrency behavior:

  • Non-blocking I/O (Async): HTTP request parsing, Pydantic validation, Redis non-blocking network calls, and async HTTP requests.
  • Synchronous Blocking Workloads: ChromaDB SQLite disk writes, PyPDFLoader text extraction, and LangChain splitter loops.

To prevent blocking the event loop during heavy document ingestion, FastAPI automatically offloads synchronous route handler functions (defined with standard def instead of async def) to an internal AnyIO worker thread pool.

💡 INTERVIEW POINT: ASYNC DEF VS DEF IN FASTAPI

"In FastAPI, defining a route as async def means FastAPI executes it directly on the main event loop. If that route calls a synchronous library like PyPDFLoader, it will freeze the server for all other users! By defining synchronous routes with standard def, FastAPI automatically schedules them on separate worker threads from a thread pool, keeping the main event loop responsive."

            self._metrics.total_miss_latency_ms += latency_ms

def query(self, question: str) -> RAGResponse:
    norm_query = question.strip().lower()
    cache_key = self.cache.generate_key(norm_query)

    # 1. Check Redis Cache
    cached = self.cache.get(cache_key)
    if cached is not None:
        return cached

    # 2. Retrieve Top-K relevant chunks
    chunks = self.retriever.retrieve(norm_query)

    # 3. Empty context guard
    if not chunks:
        return RAGResponse(
            answer="I could not find any relevant information in the uploaded documents.",
            sources=[],
            latency_ms=elapsed_ms,
            model=self.config.model
        )

    # 4. Construct grounded prompt & call LLM
    prompt = self._build_prompt(norm_query, chunks)
    raw_answer = self.llm.generate(prompt)

    # 5. Extract deduplicated citations & cache response
    citations = self._deduplicate_sources(chunks)
    response = RAGResponse(answer=raw_answer, sources=citations, latency_ms=elapsed_ms)
    self.cache.set(cache_key, response)
    return response

SensitiveDataFilter Logging Redaction

Automated logging filter intercepting log streams to redact API keys and bearer tokens.

Accidental leakage of API keys into centralized logging aggregators (e.g., Datadog, CloudWatch, Sentry) is a major enterprise security vulnerability. In backend/app/core/logging.py, NexusRAG attaches a custom logging.Filter: 

class SensitiveDataFilter(logging.Filter):
    PATTERNS = [
        re.compile(r'sk-or-[A-Za-z0-9_-]{32,}'),  # OpenRouter API keys
        re.compile(r'AIza[A-Za-z0-9_-]{35}'),     # Google GenAI API keys
        re.compile(r'Bearer\s+[A-Za-z0-9._-]+')    # JWT / Bearer tokens
    ]

    def filter(self, record: logging.LogRecord) -> bool:
        msg = record.getMessage()
        for pattern in self.PATTERNS:
            msg = pattern.sub('[REDACTED_API_KEY]', msg)
        record.msg = msg
        record.args = ()
        return True
🔒 REDACTION GUARANTEE

Even if an unhandled exception or debug trace attempts to log a configuration object containing active credentials, the filter intercepts the record before it reaches standard output, scrubbing all secrets.

⚙️ Why React 18 & Vite?
VERIFIED SELECTION

Decision: Client-side React 18 SPA bundled with Vite.

  • NexusRAG is an internal enterprise tool, not an e-commerce site requiring SEO or SSR hydration overhead.

Alternative Next.js App Router / Remix
When to Change If NexusRAG becomes a public-facing documentation hub requiring search engine crawler indexing and OpenGraph social previews.
⚙️ Why FastAPI?
VERIFIED SELECTION

Decision: FastAPI running on Uvicorn ASGI with Python 3.11+.

  • Asynchronous event loop handles high-concurrency I/O (model API gateways, vector database queries) with minimal memory overhead.
  • Built-in Pydantic integration enforces strict runtime data contracts and automated OpenAPI documentation.
  • First-class dependency injection system enables clean singleton lifespans and painless test doubles.
Trade-off Async execution requires careful handling of blocking code (sync I/O must be routed to AnyIO thread pools).
Alternative Flask (Sync) or Django (Full-stack)
When to Change Never for this API tier; would only supplement with Go/Rust microservices if raw throughput exceeds 50,000 req/sec.
⚙️ Why LangChain Core?
VERIFIED SELECTION

Decision: LangChain document loaders, recursive text splitters, and ChatOpenAI client.

  • Avoids reinventing battle-tested document parsing and boundary-aware recursive chunking algorithms.
  • Provides standardized Document schema (page_content + metadata dict).
  • Used purely as a library of utilities rather than an opaque, all-in-one execution chain.
Trade-off Frequent upstream breaking changes; heavy dependency tree if pulling full langchain package.
Alternative LlamaIndex / Raw custom parsing scripts
When to Change If package size becomes a constraint in serverless Lambda functions; would extract standalone regex chunkers.
⚙️ Why Google Gemini Embedding 2?
VERIFIED SELECTION

Decision: Google GenAI gemini-embedding-2 with 768 output dimensions.

  • High semantic density across technical prose, tabular records, and multi-language documentation.
  • Supports asymmetric retrieval tasks (RETRIEVAL_DOCUMENT vs RETRIEVAL_QUERY).
  • 768 dimensions require 50% less RAM and disk than 1536-dim OpenAI models while offering higher recall.
Trade-off External network dependency subject to Google API quotas and WAN latency (~200ms per batch).
Alternative OpenAI text-embedding-3-small / Local BGE-large-en
When to Change If documents contain classified defense or air-gapped data requiring 100% on-premises local embeddings (e.g. HuggingFace TEI).
⚙️ Why ChromaDB?
VERIFIED SELECTION

Decision: Embedded ChromaDB PersistentClient with SQLite metadata and HNSW vector index.

  • Zero external database server to deploy, monitor, or manage in development.
  • Instant local disk persistence under ./data/chroma_db.

Trade-off Embedded SQLite write locks limit FastAPI to single-process concurrency on write operations.
Alternative Qdrant / Pinecone / pgvector
When to Change At multi-pod horizontal scaling where multiple FastAPI containers must concurrently write to a shared vector database.
⚙️ Why Redis Query Cache?
VERIFIED SELECTION

Decision: Standalone Redis container caching normalized query responses with 1-hour TTL.

  • Reduces query latency from ~1.8 seconds to sub-10 milliseconds for frequent questions.
  • Slashes external LLM and embedding API expenses by up to 90%.
  • Enables simple blanket or key-based cache invalidation upon document updates.
Trade-off Introduces an external infrastructure dependency requiring Docker container management.
Alternative In-memory Python dictionary (e.g. cachetools)
When to Change An in-memory dictionary fails when scaling horizontally across multiple FastAPI processes; Redis is the correct distributed choice.
⚙️ Why OpenRouter AI Gateway?
VERIFIED SELECTION

Decision: OpenRouter gateway routing completions to google/gemini-2.5-flash.

Trade-off Adds a proxy network hop (~30ms) between our backend and the foundation model provider.
Alternative Direct Google AI Studio API / Azure OpenAI

⚙️ Why Google Gemini 2.5 Flash?
VERIFIED SELECTION

Decision: google/gemini-2.5-flash with temperature 0.2 and max_tokens 4096.

  • State-of-the-art context window reasoning and strict adherence to negative constraints ('Answer ONLY from context').
  • Blazing generation latency (~800ms) compared to heavier models (~2.5s).
  • Ultra-low per-token pricing ideal for cost-efficient enterprise deployment.
Trade-off Slightly less capable than Claude 3.5 Sonnet on complex mathematical proofs or intricate code generation.
Alternative Claude 3.5 Sonnet / GPT-4o-mini
When to Change If the domain shifts from factual corporate QA to complex multi-step code synthesis requiring Claude Sonnet.

Trade-off Limited to ~5MB browser quota; conversations do not synchronize across devices or browsers.
Alternative Server-side PostgreSQL chat session table
When to Change When implementing multi-user authentication where users expect cross-device chat sync and server-side chat export.
⚙️ Why Docker & Docker Compose?
VERIFIED SELECTION

Decision: Multi-container orchestration for FastAPI backend and Redis service.

  • Guarantees 100% environment parity across local development, CI/CD testing, and staging.

Trade-off Requires Docker Desktop daemon on local developer machines.

'Why This?' Architectural Defense Scenarios

Detailed engineering rationale for core framework, storage, and algorithm choices.

⚙️ Why React & Vite instead of Next.js?
ARCHITECTURAL DEFENSE
  • Decision: Client-side React 18 SPA bundled with Vite.
  • Reason: NexusRAG is an authenticated internal enterprise dashboard, not a public-facing e-commerce site requiring Search Engine Optimization (SEO) or Server-Side Rendering (SSR). Vite provides instant HMR and simple static hosting.
  • Alternative: Next.js App Router.
  • Trade-off: Next.js introduces Node.js server runtime complexity, SSR hydration overhead, and vendor coupling to Vercel conventions.
  • When to Change: If the knowledge base becomes a public documentation portal requiring SEO indexing and social media open-graph previews.
⚙️ Why FastAPI instead of Flask or Django?
ARCHITECTURAL DEFENSE
  • Decision: FastAPI on Uvicorn ASGI.
  • Reason: High-throughput async I/O handling, automatic OpenAPI/Swagger schema generation, and native integration with Pydantic v2 data models.
  • Alternative: Flask or Django REST Framework.
  • Trade-off: Flask requires assembling separate libraries for validation, serialization, and documentation; Django is a monolithic framework with heavy ORM overhead ill-suited for microservice RAG architectures.
  • When to Change: If the application requires a monolithic relational database administration panel with built-in session auth, where Django's admin would save engineering time.
⚙️ Why Google Gemini Embedding 2 instead of OpenAI `text-embedding-3-small`?
ARCHITECTURAL DEFENSE
  • Decision: gemini-embedding-2 via Google GenAI SDK.
  • Reason: Support for Matryoshka Representation Learning (truncated to 768 dimensions) and native asymmetric task types (RETRIEVAL_DOCUMENT vs RETRIEVAL_QUERY).
  • Alternative: OpenAI text-embedding-3-small.
  • Trade-off: Gemini SDK had subtle batch-formatting nuances that required custom handling.
  • When to Change: If the organization operates exclusively on Azure or OpenAI enterprise agreements where data processing DPAs are already established.
⚙️ Why Redis instead of an In-Memory Python Dictionary?
ARCHITECTURAL DEFENSE
  • Decision: Standalone Redis 7 container.
  • Reason: Shared state across backend processes, automatic TTL expiration, and persistence across backend server restarts.
  • Alternative: Python in-memory dictionary (cachetools.TTLCache).
  • Trade-off: In-memory dictionaries cannot be shared across multiple Uvicorn workers or container replicas; every worker maintains duplicate cache entries, and restarting the backend purges all cached answers.
  • When to Change: In embedded CLI tools or offline desktop applications where running a Redis daemon is impractical.

'What If?' System Resilience & Stress Scenarios

Concrete failure response mechanisms for production emergencies, high concurrency, and service outages.

⚠️ WHAT IF REDIS GOES DOWN COMPLETELY?
  • Current Behavior: The system logs a warning, records the error in internal metrics, and fails open.
  • User Impact: Zero downtime. Users experience a minor latency increase on repetitive queries (~1.8s instead of ~5ms) as queries fall through to the RAG pipeline.
  • Mitigation: Deploy Redis with Sentinel or AWS ElastiCache multi-AZ replication.
⚠️ WHAT IF GEMINI EMBEDDING API RETURNS HTTP 429 (RATE LIMIT EXCEEDED)?
  • Current Behavior: GeminiEmbeddingService intercepts the error, maps it to EmbeddingProviderError, and bubbles it to FastAPI, returning HTTP 500/502. The staged upload file is cleanly unlinked.
  • Production Solution: Implement an asynchronous ingestion task queue (Celery/RabbitMQ) with exponential backoff and jitter, retrying up to 5 times over several minutes rather than failing immediately.
⚠️ WHAT IF A USER UPLOADS A 1,000-PAGE PDF?
  • Current Behavior: The upload succeeds if the file is $\le 10\text{ MB}$. However, processing 1,000 pages in a single synchronous thread will tie up the worker thread for 60+ seconds, generating ~3,000 chunks and potentially hitting Gemini rate limits during batch embedding.
  • Production Solution: Reject files exceeding 100 pages synchronously. Offload long documents to an asynchronous Celery worker that splits the document into multi-page batches, writes partial progress to a database, and notifies the frontend via WebSockets upon completion.
⚠️ WHAT IF TWO USERS UPLOAD DIFFERENT DOCUMENTS WITH THE SAME FILENAME SIMULTANEOUSLY?
  • Current Behavior: _stage_upload_file prefixes each file with a random UUIDv4 ({uuid}_{filename}), preventing filesystem collisions. However, because chunk IDs use the canonical filename, concurrent writes to ChromaDB with the same filename could cause race conditions during upsert.
  • Production Solution: Assign an internal immutable UUID document_id to each upload, using {document_id}::{chunk_index} for ChromaDB IDs while displaying the human-readable filename in the UI.

Rapid-Fire Project Defense Cheat Sheet (20 Critical Points)

High-density rapid revision answers for immediate pre-interview recall.

⚡ Why RAG?
Solves LLM hallucinations and training cutoff limits; separates external factual memory from reasoning capability.
⚡ Why ChromaDB?
Embedded zero-dependency vector store; ideal for single-node prototypes without managing database clusters.
⚡ Why Redis?
Avoids repeated expensive embedding (~200ms) and LLM (~2s) calls for popular questions; delivers sub-5ms hits.
⚡ Why OpenRouter?
Standardized OpenAI REST schema; avoids vendor lock-in; allows switching models in `config.yaml`.
⚡ Why Asymmetric Embeddings?
Questions and answers have different syntax; asymmetric task types align them in latent space.
⚡ Why Recursive Chunking?
Splits text on natural grammatical breaks (`\n\n`, `\n`, spaces) rather than cutting words in half.
⚡ Why 800 Char Chunks?
Represents one cohesive semantic idea; larger chunks dilute vector density; smaller chunks lose context.
⚡ Why 100 Char Overlap?
Guarantees semantic continuity so concepts spanning chunk boundaries are not cut in half.
⚡ Why Fail-Open Cache?
Cache is an acceleration layer; a cache failure must never bring down core question-answering.
⚡ Why Skip Caching on Empty Retrieval?
Prevents cache poisoning; newly ingested documents can be queried immediately.
⚡ Why Safe Document Replacement?
Indexes new document FIRST; only deletes old vectors upon verified success, preventing catastrophic data loss.
⚡ Why Deterministic Chunk IDs?
`SHA256(source::chunk_index)` enables idempotent upserts without duplicate records.
⚡ Why Synchronous `def` on `/chat`?
Offloads blocking LLM and database I/O to a background threadpool, keeping the asyncio event loop unblocked.
⚡ Why Cosine vs L2 Distance?
ChromaDB uses Euclidean L2 squared distance (d²), where smaller numerical distance indicates closer semantic proximity in normalized latent space.
⚡ Why OpenRouter over Direct Gemini?
Acts as an abstracted multi-model gateway with standardized OpenAI API schemas, preventing vendor lock-in and allowing instant model failover.
⚡ Why Strip BOM & Whitespace?
Eliminates non-semantic token bloat, ensuring maximum informative text fits within the 800-character chunk window.
⚡ Why Single Collection?
Avoids collection switching overhead at current project scale, relying on where={'source': filename} metadata filtering for isolation.
⚡ Why UUID File Prefixes?
Staging uploads with {uuid}_{filename} isolates concurrent uploads on disk, preventing temporary file collisions.
⚡ Why Blanket Cache Invalidation?
Guaranteed consistency: any document upload, edit, or deletion immediately invalidates cached answers to prevent serving stale information.
⚡ Why 236 Automated Tests?
Comprehensive unit, integration, and API test coverage (184 backend, 52 frontend) ensures complete system stability without external network dependencies.
